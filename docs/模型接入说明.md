## 3. 预处理规范（D3，已确认）

| 项 | 取值 |
| --- | --- |
| 输入尺寸 | 288 × 288 |
| 张量布局 | NCHW |
| 通道顺序 | RGB |
| 缩放 | 短边缩放到 329（= `int(288 / 0.875)`，也就是训练说明里的 `288 × 256 / 224`），长边按比例，双线性插值（bilinear） |
| 裁剪 | 中心裁剪 288 × 288 |
| 归一化均值 | `[0.485, 0.456, 0.406]` |
| 归一化标准差 | `[0.229, 0.224, 0.225]` |
| 像素值范围 | 先除以 255，再按上表归一化 |
| crop_pct | 0.875 |

> **两个必须逐位对齐的细节（实测）**：
> 1. 缩放后的长边用 `int()` **截断**，不是四舍五入；
> 2. 中心裁剪起点用 `int(round((边长 - 288) / 2))`，**不是**整除 `//2`。
>
> 1242 × 698 的两张实测图，裁剪起点偏 1 个像素就让首位候选置信度从 64.3% 掉到 53.2%（莴笋炒虾仁）、
> 从 45.9% 掉到 38.1%（土豆肉末拌面）。这份实现已固化为 `prototype/preprocess.py`：
> 尺寸、插值、crop_pct 一律从 `models/dish.manifest.json` 读，不写死——两代权重的契约并不相同
> （第一代 224 / 双三次，第二代 288 / 双线性）。

## 4. 输出规范（D4，已确认）

| 项 | 取值 |
| --- | --- |
| 输出张量数量与形状 | 一个：`logits`，`[batch, 208]` |
| 输出含义 | 未过 softmax 的类别分数（logits） |
| 本项目的解码方式 | 先做数值稳定的 softmax，再取 top-5，返回类别下标与概率 |
| 置信度取值范围 | softmax 后为 0~1，同一张图的 208 个概率之和为 1 |
| 多标签能力 | 无。这是单标签分类模型，一张图只有一个答案，不提供检测框或掩码 |

**关于「同族类别」**：分类模型对相近菜品（如不同面食）会给出多个量级接近的概率。
实测土豆肉末拌面那张图，前三名分别是 #156 / #157 / #149，置信度 45.9% / 19.2% / 12.3%，
彼此咬得很紧。因此本项目的界面不做「只给一个答案」，而是展示 top-5 候选并提示不确定性来源，
由用户点选确认——这与原先食材识别时代由用户勾选纠错是同一个思路。

## 5. 类别清单格式（D2，已收到）

约定格式是 `labels.json`，键为类别索引（从 0 开始，与训练时输出维度一致），值为菜名：

```json
{ "0": "麻婆豆腐", "1": "红烧肉", "2": "蛋包饭" }
```

**这是最容易出错的一环**：如果索引顺序和训练时不一致，我们会把红烧肉认成蛋包饭，而且从置信度上看不出来。
请**不要**手工整理这份文件，直接从训练脚本的 `class_to_idx` 导出即可；如能同时给出英文标签与中文名，请分两个字段给。

实收的是 CSV（`Food list - Menu.csv`），已由 `backend/tools/import_labels.py` 校验并转成 `models/dish_labels.json`：
下标必须连续覆盖 0 ~ 207、菜名不能为空也不能重复，**模型输出下标直接等于 CSV 的 `List No.` 列，不重排**。
已逐项核对：208 个下标齐全、中文名无重复，且 #77 红烧肉 / #121 清炒虾仁 / #131 蛋包饭 / #157 臊子面
与第一代模型在演示图上的输出一致，可判定两代模型的类别顺序相同。

清单缺失时（例如只拷了权重去别处跑）用「类别 #N」占位，并固定标注「名称待确认」：
这条由测试守住，不允许为了好看而先编菜名。

## 6. 本项目对外提供的接口（你们不需要做任何事，仅作背景）

```json
POST /api/recognize   (multipart/form-data: file)
{
  "recognition_id": "uuid",
  "model_version": "dish-convnext-base-208-onnx",
  "class_count": 208,
  "labels_available": true,
  "degraded": false,
  "elapsed_ms": 143,
  "candidates": [
    { "index": 77, "name": "红烧肉", "confidence": 0.885, "provisional_name": false }
  ]
}
```

- `name` 由我们通过 `labels.json` 把类别下标转成菜名得到，这一步由我们负责。
- 名称与菜谱的衔接由我们的 `dish_recipe_map` 维护：能接上菜谱库的走库内做法，接不上的走大模型生成（FR-13）。
- **模型未就绪或推理异常时我们会自动降级为模拟实现**（`degraded: true`），所以你们的进度不会阻塞我们，
  但也请不要在最后一天才交付。注意：**缺少 `labels.json` 不算降级**——我们仍会跑真实模型，只是名称退化为占位。

## 10. 后端跑在哪块硬件上（v2.19 补，v2.20 补齐 GPU）

模型是 ONNX，后端用 onnxruntime 加载，跑 CPU 还是 GPU 由 `RECIPE_ONNX_PROVIDERS` 决定
（默认 `auto`：有可用的加速就用，否则 CPU；也可以写 `cpu` / `cuda` / 逗号分隔的一串）。
这两个坑接入时都实测过，写在这里免得下次重新踩：

| 现象 | 实测数据 | 后端的处理 |
| --- | --- | --- |
| 装了 GPU 版 onnxruntime **不等于**跑在 GPU 上 | `get_available_providers()` 里有 CUDA；`InferenceSession(providers=['CUDAExecutionProvider', ...]).get_providers()` 只回 `['CPUExecutionProvider']`。不抛异常、不回退到降级链；两种执行路径的 logits 最大绝对差 0.0、单张耗时 138.4 ms vs 142.8 ms | 建会话后读 `get_providers()` 作为事实来源，拿不到加速就打 WARNING（附依赖提示），并把结果写进 `/api/health` 的 `model.providers` |
| 模型加载的开销会落在**第一个用户请求**上 | 首请求墙钟 1324 ms，第二个 234 ms；而接口返回的 `elapsed_ms` 首请求只报 255 ms——加载发生在依赖解析阶段，不在计时区间里，看日志只会觉得「第一个请求怎么这么慢」 | 启动预热识别器（`RECIPE_WARMUP=0` 可关）：本机预热 1095 ms，首请求墙钟降到 197 ms |

这台机器当初缺的是 CUDA 运行库：onnxruntime 1.19 的 CUDA 提供程序要求 CUDA 12 + cuDNN 9，
而 torch 2.3.1 自带的是 cuDNN 8，于是 `onnxruntime_providers_cuda.dll` 加载失败（错误码 126）后静默回落。
按 `docs/项目设计方案.md` 7.3.2 的办法补齐 `nvidia-*` 轮子、并在建会话之前把目录挂进搜索路径之后：

- `model.providers` 变成 `["CUDAExecutionProvider", "CPUExecutionProvider"]`，会话真的拿到了 CUDA；
- 单张 288×288 前向的 p50 由 140.7 ms 降到 11.3 ms、p95 由 146.0 ms 降到 12.1 ms（50 次分位）；
- 会话加载由 381.6 ms 涨到 585.9 ms，所以启动预热（`RECIPE_WARMUP`）保持默认开启更划算；
- 9 张演示图上两个执行提供程序的 top-1 与 top-5 完全一致，logits 最大绝对差 1.617e-3。

硬件口径：RTX 4060 Laptop 8 GB，Windows 11，onnxruntime 1.19.2。没装运行库的机器行为不变，
仍然回落 CPU，`model.providers` 会把事实照实报出来。
