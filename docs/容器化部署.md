本文说明怎么用容器把前后端拉起来，以及哪些数字来自实测。所有命令都可以直接复制执行。

## 1. 解决什么问题

按 `README.md` 的本机跑法，换一台机器要做这些事：装 Python 3.9、建虚拟环境、装后端依赖、
装 Node、装前端依赖、准备 335 MB 权重、配置大模型 Key。任何一步版本对不上，都可能卡在
「在我电脑上能跑」上，演示当天尤其折腾。

容器化把这套流程固化成一个编排文件，对方机器上只需要装 Docker：

| 服务 | 镜像 | 大小 | 内容 |
| --- | --- | --- | --- |
| backend | `recipe-recognizer-backend` | 517 MB | `python:3.9-slim` + FastAPI + onnxruntime（CPU），权重与数据库由卷挂载进来 |
| frontend | `recipe-recognizer-frontend` | 72.3 MB | 多阶段构建，产物交给 nginx 托管，并把 `/api` 反向代理到后端 |

## 2. 一键启动

```powershell
docker compose up -d --build    # 构建并启动
docker compose ps               # 看两个服务的状态
docker compose logs -f backend  # 跟踪后端日志
docker compose down             # 停止（数据库留在卷里）
docker compose down -v          # 停止并清掉数据库卷
```

起来之后访问 `http://localhost:5173/`，入口与本机跑法一致。

宿主端口映射成 `127.0.0.1:8000` 与 `127.0.0.1:5173`，只监听本机，不对外网暴露。
端口号特意和本机跑法保持一致：菜谱记忆存在 localStorage 里、按 origin 隔离，
换成别的端口等于换一份记忆。

首次构建要联网装依赖，国内网络下会遇到的问题见第 5 节。

## 3. 镜像里的几个决定

### 3.1 权重不进镜像，只读挂载

`models/dish.onnx` 有 335 MB，且按仓库约定不入版本库。compose 把宿主机的 `models/`
以只读方式挂到 `/app/models`，并用 `RECIPE_MODELS_DIR` 指过去。好处是换模型时
只替换宿主机的文件，不用重新构建镜像。

### 3.2 预处理实现必须进镜像

识别精度取决于预处理与训练是否一致，所以 `backend/app/services/dish_preprocess.py`
不做第二份拷贝，按路径加载仓库里唯一那份 `prototype/preprocess.py`。

这一条是搭建时真正踩到的坑：第一次构建漏了它，容器**不会报错**，
`/api/health` 照常返回 200，只是 `model.loaded` 变成 `false`、识别走模拟实现。
报错信息藏在启动日志里（`找不到预处理实现：/app/prototype/preprocess.py`），
接口层面看不出来。`Dockerfile.backend` 里因此单独 `COPY` 了这一份实现，
同目录的 `dish.html`、`index.html` 与构建脚本则被 `.dockerignore` 挡在外面。

### 3.3 不装 libgomp1

早期版本的 onnxruntime 需要一个 libgomp 系统库，网上常见的做法是
`apt-get install libgomp1`。实测当前组合不需要：`onnxruntime 1.19.2` 在
Debian 13 的 slim 镜像里直接 `import` 就成功。

反过来，一旦引入 `apt-get`，构建就被绑在 apt 源上。Debian 13 用的是 deb822 格式的
`debian.sources`，而国内镜像站的 `dists/trixie/main/binary-amd64/Packages`
只提供压缩版，`apt-get update` 会拿到 404，配镜像加速也绕不过去。
去掉这一步之后构建只依赖 pip，链路短很多。

### 3.4 前端用 nginx 托管，不用 vite dev server

`Dockerfile.frontend` 分两个阶段：Node 阶段跑 `npm ci` 与 `npm run build`
（脚本自带 `tsc --noEmit`，类型不过就不会产出镜像），产物再拷进 nginx 镜像。

浏览器只访问一个源，`/api` 由 nginx 转给 `backend:8000`。这样容器里不需要 CORS，
也不用给前端注入 `VITE_API_BASE_URL`，前端代码里那套相对路径原样可用。

### 3.5 nginx 的上传上限要大于后端

后端单张图的上限是 5 MB，nginx 默认只收 1 MB。不显式调大的话，
大图会先被 nginx 挡掉，用户看到的是 nginx 的 413 页面，而不是后端那套结构化错误体。
`deploy/nginx.conf` 里设成 6 MB，留出 multipart 边界的余量。

同理，`proxy_read_timeout` 设成 60 秒：库外菜要现调大模型，后端自己的超时是 20 秒，
代理不能比它先放弃。

## 4. 实测数据

### 4.1 冷启动

| 项目 | 实测 |
| --- | --- |
| 无缓存构建（`docker compose build --no-cache`） | 后端 **37.6 s**、前端 15.2 s（基础镜像已在本地，依赖走国内源） |
| `docker compose up -d` 到 `/api/health` 可用 | **6.8 s**（镜像已构建，含加载 335 MB 权重与灌种子数据） |
| 容器重启到 healthy | 7 s |

### 4.2 识别与检索时延（NFR-01，各 100 次）

压测用仓库自带的 `backend/tools/perf_probe.py`，同一批样例图，三种环境各跑一轮：

| 环境 | 执行提供程序 | mean | p50 | p95 | max |
| --- | --- | --- | --- | --- | --- |
| 容器内 | `CPUExecutionProvider` | 161.0 ms | 155.1 ms | **193.5 ms** | 291.3 ms |
| 本机进程（强制 CPU） | `CPUExecutionProvider` | 160.8 ms | 157.9 ms | 172.6 ms | 192.4 ms |
| 本机进程（默认） | `CUDAExecutionProvider` | 24.0 ms | 22.3 ms | 31.1 ms | 32.3 ms |

菜谱检索（库内命中，100 次）：容器 mean 5.2 ms、p95 6.1 ms；本机 mean 4.7 ms、p95 5.8 ms。
两项都在 NFR-01 的预算内（识别 500 ms、检索 200 ms）。

这组数字说明两件事。容器对 CPU 推理的算力没有实质损失：均值 161.0 ms 对 160.8 ms，
基本重合；p95 高出的 12% 来自容器网络与调度抖动，不是模型变慢。真正的差距来自硬件，
本机那 24.0 ms 是显卡的功劳，而容器固定走 CPU，因为这台机器没有可透传给容器的独立显卡。

### 4.3 端到端链路

在容器里跑一遍完整流程（上传照片到返回菜谱）：

| 步骤 | 结果 |
| --- | --- |
| 上传 `demo/dishes/dish-mapo-tofu.jpg` | top-1 麻婆豆腐，置信度 0.8701，耗时 209 ms |
| 解析库内菜（麻婆豆腐） | `source=library`，4 步，217 ms |
| 解析库外菜（蚂蚁上树） | `source=generated`，8 步，6096 ms（真实调用大模型） |
| 同一个库外菜再解析一次 | `source=library`，9 ms（已落库，不再消耗额度） |

大模型 Key 由 compose 从仓库根 `.env` 注入到容器环境变量，不写进 compose 文件，
也不会被烤进镜像（`.dockerignore` 里排除了 `.env`）。

### 4.4 数据持久化

数据库放在名为 `recipe-data` 的卷里。上表生成的那道菜让菜谱总数从 75 变成 76，
`docker compose restart backend` 之后仍然是 76，`docker compose down` 再 `up` 也还在。

容器首次启动时库里是 75 道种子菜谱。宿主机那份 `backend/recipe.db` 里的 87 道
包含本机历史上生成过的菜，没有带进容器：容器用自己的卷，从种子数据开始。

## 5. 国内网络下构建

这台机器的网络出口连不上境外主机（`registry-1.docker.io`、`pypi.org`、
`registry.npmjs.org` 的 TLS 都会被中断），阿里云、清华、npmmirror 正常。
因此构建链路的每一段都做了处理，换到能直连的网络时按下面的办法切回官方源。

### 5.1 基础镜像

Docker Hub 拉不下来，但镜像加速器只能解决「拿清单」，拿不到 blob：
实测 DaoCloud 与 1ms 的 blob 分别放在 Cloudflare R2 与 AWS CloudFront 上，
连接同样被重置。可用的做法是走华为云 SWR 上的 Docker Hub 命名空间镜像
（国内 CDN、匿名可拉），然后在本机打上标准 tag：

```powershell
$base = "swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.io"
docker pull "$base/library/python:3.9-slim"; docker tag "$base/library/python:3.9-slim" python:3.9-slim
docker pull "$base/library/node:24-alpine";  docker tag "$base/library/node:24-alpine"  node:24-alpine
docker pull "$base/library/nginx:alpine";    docker tag "$base/library/nginx:alpine"    nginx:alpine
```

打完 tag 之后 `Dockerfile` 里写的仍是标准镜像名，不依赖任何私有仓库。

### 5.2 依赖源

两个 `Dockerfile` 把依赖源做成了构建参数，默认值走国内镜像，可以直接构建：

| 参数 | 默认值 | 切回官方源 |
| --- | --- | --- |
| `PIP_INDEX_URL` | `https://pypi.tuna.tsinghua.edu.cn/simple` | `--build-arg PIP_INDEX_URL=https://pypi.org/simple` |
| `NPM_REGISTRY` | `https://registry.npmmirror.com` | `--build-arg NPM_REGISTRY=https://registry.npmjs.org` |

`npm ci` 用 `--registry` 指定源时，npm 会把 lockfile 里指向官方 registry 的
`resolved` 地址换成这个源，所以 `package-lock.json` 不用改，完整性校验值也还是原来的。

### 5.3 Docker Desktop 的代理注入

Docker Desktop 默认继承系统代理，会把系统代理地址注入构建容器。
如果系统代理本身连不上境外，`apt`、`pip` 这类走容器的请求会拿到
`reading HTTP GET: unexpected EOF` 这类看不懂的报错。这台机器上 pip 走清华源不受影响，
所以没有改动这项设置；换成别的网络环境时，可以在 Docker Desktop 的
Settings → Resources → Proxies 里改成 No proxy 再试。

## 6. 后续可选

- **GPU 版后端镜像**：把基础镜像换成 `nvidia/cuda` 系列，装 `onnxruntime-gpu`，
  并在 compose 里加显卡预留（`deploy.resources.reservations.devices`）。
  在 Windows 上还需要容器侧的 CUDA 支持，按 4.2 节的数字，收益是 p95 从 193.5 ms 降到 30 ms 量级。
- **镜像入库**：把两个镜像推到镜像仓库，对方 `docker compose pull` 即可，连构建都省了。
