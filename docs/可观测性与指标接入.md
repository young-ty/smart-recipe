# 可观测性接入记录（request id / 日志 / 指标）

| 项 | 说明 |
| --- | --- |
| 适用范围 | 后端 FastAPI 服务：识别、菜谱解析、大模型生成三段 |
| 落地日期 | 2026-10-06 |
| 依据 | 设计方案 5.5、NFR-09 |
| 相关文件 | `backend/app/core/metrics.py`、`backend/app/core/observability.py`、`backend/app/api/routes_ops.py`、`backend/tools/metrics_report.py` |

## 1. 为什么要做

第一轮验收看的是「接口返回 200」。上一轮把推理移出事件循环、加了并发闸门（见
`识别服务并发与延迟优化记录.md`，并发 8 的吞吐 6.31 → 9.80 req/s），但这件事只能靠
专用压测脚本跑出来——服务跑起来之后，没有人知道它现在什么状态。具体缺三样东西：

1. **一条请求串不起来**。库外菜生成失败时，日志只有一句「调用大模型失败，降级为不可用」，
   看不出是哪个请求、前端点的是哪张图，也没法和前端展示的 `recognition_id` 对上。
2. **运行期没有量化数据**。识别接口 P95 175.9 ms 这个数字来自一次性压测，跑起来之后
   没有持续观测，延迟变坏只能靠用户抱怨。
3. **大模型的调用没有账**。缓存命中到底省下多少次调用、消耗多少 token，只能靠数日志行。

NFR-09 只要求「写入结构化日志」，这里往下做了一层：**日志能串链路，指标能算分位**。

## 2. 做了什么

### 2.1 request id 贯穿

- 请求头 `X-Request-ID`：进得来就沿用（网关或前端可以自己串链路），没有就生成 16 位十六进制。
- 两个出口：写回响应头；放进 `ContextVar`，于是线程池里的推理、深层服务层的日志都自动带上，
  不用一路当参数传。
- 外部传进来的 id 先过一道 `sanitize_request_id`：超过 64 字符、含控制字符（含换行）的一律丢弃重生成。
  不收拾的话，前端传一个带换行的值，日志里就能凭空多出一行，看上去像另一个请求发的。
- 中间件是**纯 ASGI** 写法，不用 `BaseHTTPMiddleware`：后者会给响应包一层任务组，
  流式响应与后台任务的时序会变，而我们的推理正好跑在线程池里。

### 2.2 日志

| 项 | 默认 | 可配 |
| --- | --- | --- |
| 格式 | 文本：`2026-10-06 17:24:59 INFO [req=...] app.api.routes_recognize: 识别完成：top1=红烧肉 置信度=0.885 推理=168 ms 排队=0 ms` | `RECIPE_LOG_FORMAT=json` 切一行一条的 JSON（`ts` / `level` / `logger` / `request_id` / `message`，异常栈单独一个字段） |
| 级别 | `INFO` | `RECIPE_LOG_LEVEL` |
| 输出流 | 强制 UTF-8 | — |

两个细节值得记：

- **UTF-8 是必须的**。Windows 上标准错误一旦被重定向到文件或管道，默认编码就退回 ANSI
  代码页（中文环境是 cp936），中文日志写进文件后采集端按 UTF-8 读是一串乱码。控制台流本来
  就是 UTF-8，切了等于没切。这个问题在实测里直接撞到了：日志文件读出来是
  `ʶ����ɣ�top1=������`。
- **噪声要压住**。根日志放开到 INFO 是为了业务日志，但 `httpx` 这类库在 INFO 上打逐请求日志
  （实测压测工具的输出里每次请求都多一行），所以 `httpx` / `httpcore` / `urllib3` / `multipart`
  固定压到 `WARNING`。

### 2.3 指标

`GET /metrics` 返回 Prometheus 文本暴露格式 0.0.4，不写进 OpenAPI 文档（它是给采集端抓的）。
没有引 `prometheus_client`：只用到三类指标，边界清楚，而部署环境已经要装 onnxruntime
这类几百兆的包，指标这层不再多引一个依赖。两条实现约束：

- **写操作加锁**。识别跑在线程池里，采集端又可能同时抓 `/metrics`；不加锁会读到
  「和值对不上桶计数」的中间态。
- **标签值转义**。路径、菜名这类值会进标签，双引号与换行不转义会让整段暴露文本变成非法格式。

指标清单见设计方案 5.5。三处口径值得单独说：

- **路径用路由模板**（`/api/recipes/{recipe_id}`）而不是真实 URL，否则每来一个菜谱 id 就长出一条
  新时间序列，采集端会被基数打爆。
- **`/metrics` 自己不计**：抓一次就污染一次延迟分布和 QPS。
- **`OPTIONS` 不计**：前端跑在 5173、后端在 8000，跨域时每个 POST 前面都跟一次预检，
  算进去请求量翻倍、p50 腰斩，读指标的人会以为服务比实际快。

### 2.4 看指标

项目没有接 Prometheus + Grafana，抓下来是一堆 `name{label="value"} 数字`。所以补了一个离线工具：

```powershell
.\.venv\Scripts\python.exe backend\tools\metrics_report.py
.\.venv\Scripts\python.exe backend\tools\metrics_report.py --url http://127.0.0.1:8000/metrics --json
.\.venv\Scripts\python.exe backend\tools\metrics_report.py --file probe.txt
```

它把文本解析回结构化数据，按计数 / 瞬时值 / 耗时分布三组渲染，分位数用桶线性插值估算。
**插值是估算，不是测量**：桶宽决定精度，且只在有限桶之间成立；分位落进 `+Inf` 桶时工具直接写
「估不出来」，不编数字。

## 3. 实测

### 3.1 链路串通（真实服务，127.0.0.1:8000）

```
响应头：X-Request-ID: manual-trace-001
服务端日志：2026-10-06 17:20:21 INFO [req=manual-trace-001] app.api.routes_recognize:
            识别完成：top1=红烧肉 置信度=0.885 推理=168 ms 排队=0 ms
```

请求头带进来的 id 一路进到了业务日志，`elapsed_ms` 与日志里的推理耗时也对得上。

### 3.2 指标内容（同一轮真实流量）

| 样本 | 值 | 说明 |
| --- | --- | --- |
| `http_requests_total{method="POST",path="/api/recognize",status="200"}` | 1 | 正常识别 |
| `http_requests_total{method="POST",path="/api/recognize",status="415"}` | 1 | 手动构造的错误 Content-Type，被挡在路由里，同样计入 |
| `recognize_requests_total{outcome="ok"}` | 1 | `degraded` 分支单独一档 |
| `recognize_in_flight` | 0 | 请求结束后名额还回去了；不为 0 就说明闸门泄漏 |
| `recipe_resolve_total{source="library"}` | 1 | 「红烧肉」命中库内 |
| `recipe_resolve_total{source="unavailable"}` | 2 | 库外菜 + 生成不可用 |
| `recipe_cache_total{result="miss"}` | 2 | 生成结果缓存未命中 |
| `generator_requests_total{outcome="error"}` | 2 | 本机沙箱里出网被拒（`WinError 10013`），失败也是可见的一档 |
| `/metrics` 自身 | 未出现 | 自排除生效 |

### 3.3 并发压测下的指标（`concurrency_probe.py --levels 1,4,8 --rounds 3`）

| 并发 | 吞吐 (req/s) | 探测端 p50 | 探测端 p95 | 健康检查 p95 / max |
| --- | --- | --- | --- | --- |
| 1 | 5.99 | 164.9 ms | 169.6 ms | 16.4 ms / 17.2 ms |
| 4 | 9.24 | 411.7 ms | 449.8 ms | 39.4 ms / 41.3 ms |
| 8 | 10.15 | 588.5 ms | 777.5 ms | 70.5 ms / 95.5 ms |

同一批流量在 `/metrics` 上的读数（40 次识别，桶插值）：

| 指标 | n | p50 | p95 |
| --- | --- | --- | --- |
| `http_request_duration_seconds{path="/api/recognize"}` | 40 | 416.7 ms | 916.7 ms |
| `recognize_inference_seconds` | 40 | 388.9 ms | 488.9 ms |
| `recognize_queue_seconds` | 40 | 0.7 ms | 454.5 ms |
| `http_request_duration_seconds{path="/api/health"}` | 54 | 8.2 ms | 24.2 ms |

两处对得上：`recognize_inference_seconds` 的 p50（388.9 ms）落在探测端 p50（588.5 ms）之下，
差值就是排队 + HTTP + 写库；健康检查 p95 在个位数到几十毫秒，说明推理确实没再回到事件循环里。

## 4. 边界与取舍

| 边界 | 现状 | 影响 |
| --- | --- | --- |
| 单进程 | 指标存在进程内存里 | 多 worker 部署时每个 worker 各有一套计数，采集端要按实例标签聚合；本项目单进程运行 |
| 分位数来自桶插值 | 桶边界之间按均匀分布假设 | 只用于看趋势与告警，不作为验收数字；NFR-01 的 P95 仍以 `perf_probe.py` 的实测为准 |
| `/metrics` 无鉴权 | 与业务接口同端口开放 | 本地演示可接受；对外部署要改成只给内网或加采集端鉴权 |
| 指标清零 | 进程重启即归零 | counter 语义本来就如此，不做持久化 |
| 日志采集 | 只输出到标准错误 | 没有接采集端；JSON 格式就是为接入留的口子 |
