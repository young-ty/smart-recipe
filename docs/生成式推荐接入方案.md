| 项目 | 基于深度学习的智能菜谱识别 · 大模型菜谱生成与视频入口 |
| --- | --- |
| 文档版本 | v2.1 |
| 编写日期 | 2026-09-16（v2.1 增补第 13 节：生成层加固与真实复测，2026-10-06） |
| 适用范围 | FR-13（生成式菜谱生成与解读）、FR-14（视频教程入口） |
| 关联文档 | `docs/项目设计方案.md` 第 2、5、7 章；`docs/模型接入说明.md` |
| 前置条件 | 识别 → 菜谱的链路已跑通，`backend/app/data/seed_recipes.json` 与 `recipe_resolver.py` 作为库内候选来源 |

> 缓存表为 `generated_recipes`（键 `sha1(dish + prompt_version)`）。**已落地**：先查库后生成（有测试守住库内命中不调用大模型）、

## 1. 定位：候选与检索不变，大模型只补库里没有的部分

链路分成两段，顺序固定：

1. **识别产出候选**：`POST /api/recognize` 返回 top-5 菜品候选（类别下标 + 置信度），这一步完全不涉及大模型。
2. **检索决定来源**：`backend/app/services/recipe_resolver.py` 按菜名（含别名）查菜谱库。
   命中则返回库内记录，**不调用大模型**；未命中才进入生成分支。
3. **生成只补空**：大模型负责给库外菜写出完整做法（名称、时长、难度、份量、主辅料、步骤），
   并在库内命中时按需补充解读（为什么这么搭配、缺料怎么替代）。

大模型在这里是**生成层**，不参与候选的产生与排序：

- **筛选仍由识别与检索完成**——候选集合由模型输出决定，库内命中优先，避免同一道菜在两次刷新之间给出不同结果；
- **生成结果必须可缓存、可复现**——同一道菜第二次请求不再产生外部调用（命中缓存，或生成结果已落库而直接命中库内），演示与回归测试因此稳定；
- **落库要可辨认、可回退**——生成成功的菜谱写回 `recipes` 时打上 `origin = generated`，与人工整理的 `seed` 数据区分开，页面也要标出来源；`RECIPE_PROMOTE_GENERATED=0` 可以整体关掉落库。

代价要显式接受：**不引入向量库、不做语义召回**。库外菜的覆盖能力取决于大模型的常识，
它的输出只作为"能照着做"的参考，并始终带来源标注。

## 2. 现状与差距

| 项 | 现状 | 接入后要补的差距 |
| --- | --- | --- |
| 库内菜谱 | `seed_recipes.json` 98 道，含主辅料与步骤 | 不变，命中时直接用 |
| 库外菜品 | 识别能给出候选，但库里没有对应菜谱，页面只能显示"暂无菜谱数据" | 由大模型生成完整做法，并标注来源为生成 |
| 推荐理由 | 只有「菜谱库 #109」这类来源角标 | 生成时附一句"为什么这么做"的说明 |
| 缺料处理 | 无 | 生成时给出替代主料 |
| 视频 | 无 | 一键跳到该菜的教学视频 |

**覆盖缺口的量级**：208 类里目前有 73 类能承接库内菜谱（64 类精确同名，再加 9 条别名映射，见设计方案 7.1），4 张演示图有 3 张要走生成——
也就是说，这条能力不是"锦上添花"，它是库外菜唯一的出口。

## 3. 接口设计

**主接口**（已有规划，见设计方案 5.3.2）：

```
POST /api/recipes/resolve
```

请求：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `dish` | string | 是 | 菜名；类别清单未到位时可传「类别 #77」，此时只走生成分支 |
| `index` | int | 否 | 类别下标，用于日志与缓存键 |
| `refresh` | bool | 否 | 默认 `false`，命中缓存直接返回；`true` 强制重新生成（**未实现**，属规划项） |

响应：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `source` | `"library"` \| `"generated"` \| `"unavailable"` | 库内命中 / 大模型生成 / 库内没有且生成不可用 |
| `degraded` | bool | 是否走了降级路径，`unavailable` 时恒为 `true` |
| `recipe` | object \| null | 菜谱对象：`name`、`cook_time_minutes`、`difficulty`、`rating`、`servings`、`description`、`required[]`、`optional[]`、`steps[]` |
| `recipe.video_url` | string | 由后端拼接的视频搜索链接（FR-14） |
| `reason` | string \| null | **不可用**分支的原因文案；库内命中与生成成功时为 `null`（推荐理由为规划项，尚未落地） |
| `substitutions` | object[] | `{ missing, replace_with }`，无替代时为空数组（**未实现**，属规划项） |

**可选增量接口**（P1，库内菜的解读）：

```
POST /api/recipes/{recipe_id}/explain
```

库内菜谱本身不需要生成做法，但如果时间允许，可以给它加一层解读（推荐理由、替代主料、采购清单）。
这条接口的降级路径与主接口一致，只是回退内容为种子数据本身（见第 6 节）。

## 4. 生成契约与结构化校验

发给模型的输入只有两样：**菜名**、**本项目要求的输出结构**。
**不发送用户上传的照片**，不发送任何身份信息，也不发送类别清单等内部文件。

要求模型返回固定 JSON（`name` / `cook_time_minutes` / `difficulty` / `servings` /
`description` / `required` / `optional` / `steps`），后端用 Pydantic 校验，
**命中任一条即整条降级**：

- JSON 解析失败；
- 字段缺失或类型不符；
- `steps` 为空、全是空白、超过 15 条，或其中够长的（≥ 6 字）不足 3 条——**步骤质量门槛**（v2.12）：够短的条目只参与计数、不剔除，卡的是整份输出都「照着做不到」的结果；
- `name` / `cook_time_minutes` / `servings` / `difficulty` 不在约定取值内；
- 输出中出现了 URL（理由见第 5 节）。

结构过关**还不算数**，返回之前还要过一道`RecipeResolver._sanitize_generated` 闸门（v2.12，两道规则分别对应「答非所问」与「食材挂不上」）：

| 检查 | 不通过时 |
| --- | --- |
| `normalize(name)` 必须等于本次请求的菜名 | 整条降级为 `unavailable`（给一份别的菜的菜谱比说不出更糟） |
| 主辅料要能按名字或别名挂到 `ingredients` 表 | 挂不上的从**当次结果**里剔除并记 warning；主料一样都挂不上则整条降级 |

闸门排在写缓存与落库**之前**，所以「当次返回的菜谱」和「入库后查到的菜谱」是同一份；
命中缓存时同样要过闸，旧缓存里的不干净结果当未命中处理，重新生成。

**v2.22 起输入侧与解析侧各补了一层**：菜名单独走 user 消息、用书名号定界并先去掉控制符与
零宽字符（角色与输出契约放 system 消息）；解析前先按括号配对截出 JSON 对象，围栏与寒暄不再
误判成失败；连接阶段失败重试一次。实测数据与原因见第 13 节。

**不做流式输出**：页面先给出菜名与来源角标，生成完成后再整体渲染，避免半截内容闪烁。

## 5. 视频链接由后端拼接，不采信模型直出的 URL

大模型给出的链接会指向不存在的页面，且无法在演示前逐条验证。视频入口一律由后端生成：

```
https://search.bilibili.com/all?keyword={urlencode(菜名 + " 做法")}
```

菜名来自识别结果与菜谱记录，链接因此永远落在一个真实存在的搜索结果页上。
模型不参与链接的产生。

校验方式：响应中的 `video_url` 必须等于后端按模板拼接的结果；
模型输出里出现 `http` 即判定该次生成不合格，直接降级为 `unavailable`。

## 6. 降级与缓存

沿用识别模块已有的约定：**能力可以没有，接口契约不能变。**

| 场景 | `source` | `degraded` | 行为 |
| --- | --- | --- | --- |
| 库内命中 | `library` | `false` | 直接用种子数据，不调用大模型 |
| 未配置 API Key | `unavailable` | `true` | 这次调用没有可用凭据（请求头与账号里都没有，服务端不预置 Key），不发起外部调用，页面提示去填自己的模型 Key；库内菜谱照常返回 |
| 调用超时（默认 20 s，见 `RECIPE_GENERATOR_TIMEOUT_SECONDS`） | `unavailable` | `true` | 同上，并写一条结构化日志 |
| 非 2xx 响应 | `unavailable` | `true` | 同上 |
| 结构化校验失败 | `unavailable` | `true` | 同上，**不写入缓存** |
| 步骤质量不达标 | `unavailable` | `true` | 条数或单条字数不到门槛（见第 4 节），同上，**不写入缓存** |
| 生成结果答非所问 | `unavailable` | `true` | 返回的菜名与请求的不一致，同上，**不写入缓存** |
| 主料全挂不上食材字典 | `unavailable` | `true` | 这菜谱用不了，宁可说不出，同上，**不写入缓存** |
| 正常返回 | `generated` | `false` | 写入缓存后返回；落库开关打开时同时写回 `recipes` |
| 落库失败 | `generated` | `false` | 不影响本次回答：仍然返回生成结果，只是库里没留下这条记录（日志里有 warning） |
| 解读接口失败（库内菜） | `seed` | `true` | 回退种子数据本身：步骤用库里的，理由与替代料留空 |

库外菜**没有可回退的 seed 内容**（这正是它需要生成的原因），所以它的降级表现是"明确说不出"，
而不是"退回到一份看起来像样的假菜谱"——后者会让使用者误判系统能力。

缓存落在 SQLite 的 `generated_recipes` 表，键为
`sha1(dish + prompt_version)`。命中缓存不产生外部调用，演示与回归测试因此可重复；
`prompt_version` 变化时旧缓存自然失效。

**缓存与落库是两级，不要混为一谈**（v2.7）：

| | 缓存（`generated_recipes`） | 落库（`recipes.origin = generated`） |
| --- | --- | --- |
| 写什么 | 结构化输出的 JSON 快照，保留 `model` 与 `prompt_version` | 正式菜谱记录：主表 + 主辅料 + 步骤，必要时认领显式留白的类别 |
| 谁优先 | 查库未命中后才轮到它 | 它就是库内菜谱，**「先查库」那一关直接命中** |
| 失效方式 | 换 `prompt_version` 即弃用 | 已是库内菜谱，不受提示词版本影响，只能人工改 |
| 能否关掉 | 始终写，是兜底 | `RECIPE_PROMOTE_GENERATED=0` 可关 |

注意：**命中缓存也会触发一次落库**——缓存里可能存着落库能力上线前生成的内容，若只在新生成时落库，「这道菜能不能进库」就取决于它以前有没有被缓存过，行为不可预期。现在凡是返回 `source = generated` 的路径都会尝试落库。

落库的收益是「同一个缺口只花一次额度」，代价是生成结果被固化进库——所以它必须带 `origin` 标记（界面显示「大模型生成后自动入库」，不冒充人工整理），
且**不改写种子文件**：要把某道自动入库的菜变成正式数据，仍走 `tools/draft_recipes.py` 的起草 → 审校 → 合并流程。

## 7. 性能预算

大模型首次生成在秒级，与 NFR-01 的毫秒级预算不是一个量级，所以：

- 识别与菜谱检索**不调用**生成层，NFR-01、NFR-03 的既有指标不变；
- 只在库外菜需要补做法时按需调用，且识别结果先渲染、生成结果后填充；
- 这条接口自身的 P95 预算按 **8 s** 计（实测 3~7 秒返回），单次超时上限默认 20 s 后降级，不阻塞页面上的其他交互。

## 8. 隐私与合规

- **不发送用户上传的照片**，只发送菜名；
- 用户自己的 API Key 不进版本库：未登录时只在本机浏览器 `localStorage` 里、随请求头来去；登录后由服务端加密落库（`users.llm_api_key_enc`），加密主密钥来自环境变量 `RECIPE_SECRET_KEY` 或自动生成的 `backend/secret.key`，两者都在 `.gitignore` 里，不入库；
- 缓存表只存生成结果，不存用户标识与图片摘要。

## 9. 验收标准

| 编号 | 验收项 | 判定方式 |
| --- | --- | --- |
| A1 | 无 Key 环境可用 | 不配置 Key 时 `/resolve` 对库外菜返回 200，`source="unavailable"`、`degraded=true`，提示里说明要填自己的模型 Key；库内菜仍正常返回 `library`。服务端不预置 Key，所以这是默认状态 |
| A2 | 结构化输出可控 | 20 次采样中 schema 校验通过率 ≥ 95%，失败样本全部落到降级路径且不写缓存 |
| A3 | 无编造链接 | `video_url` 必须等于后端按模板拼接的结果；模型输出含 URL 时该次判为不合格 |
| A4 | 缓存与落库生效 | 同一 `dish` 的第二次请求不产生外部调用（打桩计数为 1）：落库打开时命中库内（`source` 由 `generated` 变 `library`），关闭时命中缓存 |
| A5 | 既有指标不退化 | 仓库全量测试通过，识别接口 P95 仍 ≤ 500 ms、库内命中请求 P95 仍 ≤ 200 ms |

## 11. 与识别链路的关系

菜谱侧与识别链路互不依赖：识别侧等模型交付类别清单与样例（见 `docs/模型接入说明.md` 第 1 节），

## 12. 接入实测（2026-09-22）

Q1 已收口：用 **DeepSeek**，OpenAI 兼容接口 `https://api.deepseek.com/v1`，默认模型 `deepseek-flash`。

| 项 | 实测结果 |
| --- | --- |
| Key 读取 | 服务端不读 `.env` 里的开发方 Key（那只给本机工具用）。凭据取「请求头 `X-LLM-Api-Key` → 账号里加密存的那把」；账号那把的加密主密钥来自环境变量 `RECIPE_SECRET_KEY`，缺省自动生成 `backend/secret.key`（已 gitignore） |
| 可用模型 | `GET /v1/models` 返回 `deepseek-flash`、`deepseek-v4-pro`；`deepseek-chat` 也能调通但不在列表内，故默认取列表中显式列出的 `deepseek-flash` |
| 真实生成 | 「蛋包饭」（类别 #131，库内无承接）→ `GeneratedRecipePayload` 校验通过：主料 5 项、步骤 6 步，端到端约 5 s，落在 8 s 预算内 |
| 降级路径 | 未配置 Key 时 `/resolve` 仍返回 200 且 `source="unavailable"`，由 `backend/tests/test_recipe_resolver.py` 与接口测试守住 |
| 复现命令 | `cd backend` 后跑 `..\.venv\Scripts\python.exe -m tools.check_generator --models --live`；默认模式不联网，`--models` 与 `--live` 各消耗一次真实调用 |
| 落库 | 生成结果写回 `recipes`（`origin = generated`，id ≥ 10000），同名第二次请求 `source` 由 `generated` 变 `library`、大模型不再被调用；由打桩用例守住（`backend/tests/test_recipe_resolver.py`、`backend/tests/test_api.py`），真实网络下的表现按第 6 节口径人工复核 |

口径不变的部分：**用户上传的照片始终只用于本地识别，不外发**；生成请求体里只有菜名；模型直出的 URL 一律不采信，
`video_url` 仍由后端按模板拼接（第 5 节）。开发方那把 Key 只从环境变量 / `.env` 读给本机工具，脚本与健康检查都只回显长度与前缀；线上请求链路用的是调用方自己的凭据。

> 安全提醒：`.env` 里那把 Key 现在只给本机工具用（服务端不读它），但既然在对话里出示过，提交公开仓库或交给别人演示前仍建议在控制台**重置一次**；新 Key 只写进本地 `.env`，`backend/secret.key` 同样不要提交。

## 13. 生成层加固与真实复测（2026-10-06）

打桩用例全绿不等于真实调用可用。这轮把提示词与解析两侧收紧，同时用真实 Key 复测了一遍。

| 改动 | 为什么 |
| --- | --- |
| 角色与输出契约移入 system 消息，菜名单独走 user 消息、用书名号定界，并声明「只当菜名看」 | 手输菜名（FR-10）是自由文本，和指令挤在同一条消息里就有被当成指令读的余地 |
| 菜名进提示词前去掉控制符与零宽字符，超过 64 字截断并记 warning | 看不见的字符既会污染缓存键，也可能被模型当成另一条指令读；`normalize_dish` 用的是同一个清洗函数 |
| 解析前先按括号配对截出第一个 JSON 对象 | 兼容实现会把结果包进 ```json 围栏或加一句寒暄，这种正常输出不该判成失败 |
| `max_tokens = 4096`，并在 `finish_reason = length` 时单独记一条 warning | 见下表：这个模型把 reasoning token 也算进上限，上限给小了正文会被截成半截 JSON |
| 连接阶段失败（`ConnectError` / `ConnectTimeout`）重试一次，读超时不重试 | 请求没送到服务端时重试不重复计费；读超时说明模型可能已经在跑，重试等于再花一次额度 |
| 输出里出现 `http` 即判本次生成失败 | 第 5 节的约定此前只做到「丢弃字段」，现在是真的拦下 |

**实测：`max_tokens` 把推理 token 一起算进去。** 用同一个菜（蛋包饭）逐档试出来的：

| 上限 | 结果 |
| --- | --- |
| 200 | reasoning 吃掉全部 200，`content` 为空，`finish_reason = length` |
| 600 | `content` 只剩 37 字，JSON 截断，`finish_reason = length` |
| 1500 | 偶发被推理吃光（首次联调就撞上一次，表现为「生成结果里找不到 JSON 对象」） |
| 4096 | 连续多次通过；实测一份家常菜谱 `completion` 落在 1200 到 1900 之间，偶发到 3000 上下 |
